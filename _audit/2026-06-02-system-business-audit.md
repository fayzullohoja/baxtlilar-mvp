# Baxtlilar — системный и бизнес-аудит (2026-06-02)

Многоагентный аудит: 8 направлений (auth, онбординг, приватность, матчинг, чат, админка, целостность данных, готовность к запуску) → адверсариальная верификация блокеров/мейджоров.
**64 находки**: 5 блокеров, 27 мейджоров, 29 минор, 3 нит. Ниже — дедуплицировано и сгруппировано в план.

## P0 — БЛОКЕРЫ (до выдачи реальным пользователям)

### B1. Фото профиля в ПУБЛИЧНОМ бакете (#14, system/privacy)
Фото лиц лежат в public-бакете `profile-photos`, отдаются через `getPublicUrl` → постоянная ссылка без токена и без срока. Любой со ссылкой (даже неавторизованный) открывает фото; путь = сырой UUID → можно перебирать. При бане фото НЕ удаляются. Все серверные гейты (published/approved/block/active) обходятся знанием URL. Для брачной аудитории УЗ — реальный вектор сталкинга/доксинга, нарушение инварианта 1.
**Фикс:** сделать бакет приватным (как `user-documents`), отдавать фото только через `createSignedUrl` (короткий TTL) на сервере при рендере; на ban/hide/delete — удалять/блокировать объекты.
**Проверка:** `getPublicUrl` нигде не остаётся для фото; неавторизованный GET по старому пути → 400/403; e2e: забаненный → его подписанные ссылки протухают.

### B2. Жалобы уходят «в никуда» (#29/#54/#39, business/safety)
Таблица `reports` только пишется (`report/route.ts:24`); ни одного чтения, нет экрана в админке, `status` никогда не меняется. Модератор не видит жалобы → безопасность и юр. due-care не закрыты.
**Фикс:** `/admin/reports` + API (список с join target/reporter, переходы статусов new→reviewing→resolved/rejected, ссылки на ban/photo/verification, запись в `admin_audit_log`); эскалация при N жалоб.
**Проверка:** e2e: report → появляется в очереди → модератор резолвит → статус и аудит записаны.

### B3. Блокировка не работает внутри чата (#30/#43, business/safety)
`blocks` читается ТОЛЬКО при создании интереса. Эндпоинты чата (messages/stream/typing/read, `getChatList`) авторизуют только по участию. После блокировки обидчик продолжает писать и слать пуши жертве; экрана/эндпоинта разблокировки нет.
**Фикс:** в messages POST (и stream/list) — проверка `blocks` в обе стороны → 403 + без пуша; чат с блоком скрывать/замораживать; добавить эндпоинт разблокировки.
**Проверка:** e2e: A блокирует B → B шлёт → 403, пуш не уходит, чат у A скрыт; разблокировка возвращает.

### B4. Нет реальных ToS/Политики/Оферты (#55, business/legal)
Чекбоксы согласия ссылаются на «правила платформы и политику конфиденциальности», роут пишет 4 типа согласий — но самих документов нет нигде.
**Фикс:** опубликовать ToS + Политику обработки ПД + публичную оферту (RU/UZ), привязать к чекбоксам, версионировать, хранить версию на каждый `consent_type`.
**Проверка:** документы доступны по ссылке; согласие хранит версию.

### B5. (известный) SMS=mock + fail-open (#58, system/launch)
Сверх известного мок-блокера: ветки eskiz/playmobile — молчаливые no-op, **возвращают успех**; `sendOtp` не проверяет результат `sendSms`. На проде без ключей верификация телефона обходится «успешно».
**Фикс:** неподключённый провайдер должен БРОСАТЬ; `sendOtp` пробрасывает ошибку (`{ok:false}`) и показывает её пользователю; подключить Eskiz.
**Проверка:** без ключей OTP-отправка → ошибка, не «успех».

## P1 — МЕЙДЖОРЫ (до публичного запуска)

### Аутентификация / сессии
- **M1. Сессия не протухает (#0):** `getSessionUserId` проверяет только HMAC, не `iat`. → проверять max-age (как в admin `session.ts`), в идеале session_version в БД.
- **M2. Роль админа из куки, не из БД (#1/#37):** ban/unban читают `session.role`; снятие прав не действует до перелогина. → читать роль из `admin_users` на каждый запрос.
- **M3. Троттл логина fail-open (#2):** `count` не проверяет `error` → при сбое БД `count=null` → пускает. → fail-closed (`if(error) return true`).
- **M4. Окно initData 24ч, без single-use (#3):** реплей 24 часа. → окно ≤1ч + кэш использованных (telegram_id, auth_date).

### Онбординг
- **M5. Гонка лок-аута OTP (#7):** read-compare-write по попыткам неатомарен. → атомарный `UPDATE ... attempts+1 WHERE attempts<5 RETURNING`.
- **M6. SMS-бомбинг (#8):** троттл OTP только по `user_id`, не по `phone`. → лимит по номеру (и глобальный дневной на номер).
- **M7. Publish не смотрит статус фото (#9):** publish/photos-done проверяют только `count>0`, не `status`. Активная анкета может висеть без одобренного фото. → требовать ≥1 approved/pending + показывать «фото на проверке/отклонено».

### Приватность
- **M8. Неполное стирание при удалении (#15):** soft-delete чистит телефон+файлы, но НЕ `user_profiles` (имя, ДР, город, био, вера…), quiz, consents, user_documents-строку. → полное стирание ПД в ветке delete.

### Матчинг
- **M9. Квота просмотров мертва (#19):** `views=30` и `checkAndIncrement('views')` определены, но не вызываются. → подключить (или убрать) + дедуп match_views.
- **M10. Гонка/неатомарность квоты интересов (#20/#45/#62):** read-then-upsert, абсолютная запись. → атомарный `UPSERT ... interests_sent+1 WHERE < limit RETURNING`.
- **M11. Обход блока при взаимном блоке (#21):** `.or(...).maybeSingle()` при двух строках → error → `data=null` → «не заблокирован». → `limit(1)`/count.
- **M12. Зависшие pending скрывают людей навсегда (#22/#52):** ленивое истечение 72ч; RPC ленты исключает любой pending без `auto_decline_at>now()`; крона нет. → добавить `auto_decline_at>now()` в исключение ленты + sweep (pg_cron/Vercel cron).
- **M13. Повторный интерес после отказа = харассмент (#23):** guard смотрит только pending/accepted своей стороны; после decline можно слать снова. → кулдаун/исключить declined-пару из ленты и пере-отправки.
- **M14. Гонка авто-взаимности (#24/#44):** reverse-detect+accept+ensureChat неатомарны. → один RPC с `SELECT ... FOR UPDATE`/advisory lock.

### Чат
- **M15. Обход анти-контакт фильтра (#31):** пробелы между цифрами, кириллические цифры-двойники, разбивка по строкам. → нормализация (NFKC, zero-width, lookalikes, схлопывание пробелов между цифрами) + расширить паттерны мессенджеров.
- **M16. Нет лимита сообщений → флуд + пуш-спам (#32/#60):** только cap 2000. → rate-limit на сообщение + дебаунс `notifyUser` (и не слать пуш, если получатель в чате).
- **M17. Стоимость SSE на масштабе (#33/#59/#51):** per-viewer опрос БД 2 запроса/1.5с × 45с. → Supabase Realtime / LISTEN-NOTIFY (это Уровень 3), иначе шире TICK и объединить запросы.

### Админка / целостность
- **M18. Ban пишет blocked_at напрямую до transition (#38):** ломает оптимистичный concurrency (invariant 8). → завести blocked_at/reason в тот же RPC перехода.

### Запуск
- **M19. Тупики «обратитесь в поддержку» без канала (#56):** blocked/rejected/phone-taken просят поддержку, которой нет. → реальный контакт (Telegram @username/deep-link) кнопкой.
- **M20. Report/Block недоступны из чата (#57):** только из карточки профиля; в самом чате — лишь статичная подсказка. → добавить report+block в шапку чата (с chat_id в report).

## P2 — МИНОРЫ / доработки логики (после запуска)

- **Бизнес-правила:** возрастной ценз 25+/30+ не проверяется, только 18+ (#13); ретрай-абьюз после reject (#10); скоринг занижает тех, кто без квиза (#25); дедуп/лимит на report (#35); монетизация отсутствует (#63); funnel-аналитика отсутствует (#61); целостность согласий (#17).
- **Приватность/админ:** админ видит сырой телефон без аудита (#41/#16); `getMiniProfiles` без фильтра lifecycle → устаревшие данные в списке чатов (#18).
- **Матчинг/данные:** неустойчивый порядок ленты без tie-break (#26); off-by-one возраст JS vs SQL (#27); граница суток квоты в UTC, не Ташкент (#46); `match_views` растёт без чистки (#53); OTP принимает 4-6 цифр (выдаём 6) (#11); атомарность invalidate-then-insert OTP (#12).
- **Данные/устойчивость:** `getCurrentUser` отдаёт удалённых + `.single()` может дать 500 (#50); гонка `is_main` при удалении главного фото (#49); точность аудит-лога перехода (#47); прямые UPDATE сиблингов обходят оптимистичный concurrency (#48); IDOR-ноуп на произвольный id (#40); bootstrap без rate-limit (#4); переиспользование одного SESSION_SECRET для user+admin (#5); коллизия temp-id (#36).

## План дебага и доработки — порядок

**Фаза 0 (безопасность/доверие, до любых реальных юзеров):** B1 фото→private+signed, B2 очередь жалоб, B3 блок в чате + разблокировка, B5 SMS fail-open→Eskiz, B4 юр-документы. Дополнительно из P1: M19 поддержка, M20 report/block в чате (закрывают safety вместе с B2/B3).
**Фаза 1 (целостность/абьюз, до публичного запуска):** M10/M14 атомарность квоты и взаимности (RPC+локи), M11 фикс блок-проверки, M5/M6 OTP гонка+бомбинг, M12/M13 истечение pending + анти-повтор, M7 publish vs статус фото, M8 полное стирание ПД, M1–M4 сессии/роль/троттл/реплей, M18 ban через RPC, M9 квота просмотров, M15/M16 анти-контакт+флуд.
**Фаза 2 (масштаб/продукт):** M17 Realtime для чата (Уровень 3), P2-доработки (возрастной ценз, аналитика-воронка, монетизация-хуки, чистки/дедуп, мелкие гонки).

**Подход к проверке:** на каждый фикс — прод-e2e в узком тест-диапазоне `telegram_id 999000000–999099999` (как в текущих скриптах) + сверка инварианта (privacy/блок/квота/согласие). Storage-чистка только через Storage API.
