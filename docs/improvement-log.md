# Baxtlilar — журнал непрерывных улучшений

Этот файл ведёт автоматический цикл улучшений (`/loop`, каждые 10 минут).
Цель цикла: искать баги — **системные и бизнесовые** — исправлять их, улучшать
код там, где можно сделать лучше, и документировать каждое изменение.

**Правила цикла:**
- Один логический шаг за итерацию: найти → исправить → протестировать
  (`pnpm test:run` / `pnpm typecheck`) → задокументировать здесь → при готовности
  задеплоить (`railway up` или push в `main` = автодеплой Railway).
- Ничего полусырого в `main`. Прод-БД мутации откатываются после тестов.
- Каждая запись: **дата · что нашли · почему это баг · как починили · как проверили**.

## 2026-06-17 · Итерация 1 — silent-empty/false-404 на всех страницах админки

**Что нашли (системный + бизнесовый баг).** Аудит показал, что embed-синтаксис в
коде приложения вычищен полностью (остались только намеренные regress-тесты). Но
сам *класс* «тихо-пустых» страниц шире embed: **все оставшиеся страницы админки
читали `const { data } = await sb…` и игнорировали `error`**, подставляя `?? []`,
`?? 0`, `?? null`. Значит при ЛЮБОМ сбое БД (обрыв пула, таймаут) страница молча
показывала «пусто», а не ошибку:
- `/admin` (дашборд) — «0 заявок на проверке / 0 жалоб» → модератор не видит бэклог;
- `/admin/verifications` — «Очередь пуста» → заявки на верификацию зависают незаметно;
- `/admin/verifications/[id]` — `maybeSingle()`→null→`notFound()` → **ложный 404** на
  реально существующего пользователя;
- `/admin/reports` — «Открытых жалоб нет»;
- `/admin/analytics` — «Нет данных».

Это бизнес-риск: модерация принимает «тихо-пусто» за «работы нет».

**Как починили.**
- `src/lib/db/unwrap.ts` — к `unwrapRows` добавлены два хелпера:
  - `unwrapCount({count,error})` → бросает на error, иначе `count ?? 0` (для
    `select('*',{count:'exact',head:true})` на дашборде);
  - `unwrapOne({data,error})` → бросает на error, иначе `data ?? null` (для `rpc()` и
    `maybeSingle()`; отделяет «реально нет строки» от «БД упала»).
- Применены ко всем 5 страницам: `/admin` (page.tsx), `/admin/analytics`,
  `/admin/reports`, `/admin/verifications`, `/admin/verifications/[id]`.
- Поведение happy-path не меняется; меняется только сбойный путь: видимая 500
  вместо ложного «пусто»/404.

**Как проверили.**
- `pnpm typecheck` — чисто.
- `pnpm test:run` — 98 тестов зелёные (добавлено 6: по 3 на `unwrapCount`/`unwrapOne`).
- `pnpm lint` — изменённые файлы чисты (остаются прежние `any`-ошибки в
  `query-builder.ts` — см. бэклог ниже).

**Бэклог (найдено, отложено — не в скоупе этой итерации):**
- `src/lib/db/query-builder.ts` и `query-builder.test.ts` — 7 ошибок eslint
  `no-explicit-any`. Эти `any` несущие (на них опирается вывод типов строк во всех
  call-site'ах админки); правильный фикс — точечный `eslint-disable` с пояснением,
  а не замена на `unknown`. Не блокирует сборку (`next build` не гейтит на eslint).

## 2026-06-17 · Итерация 2 — ложный «успех» на сбое записи (safety + потеря данных)

**Что нашли (бизнес/safety-баг).** Зеркало итерации 1, но на пути ЗАПИСИ: три
пользовательских роута выполняли `insert/upsert/delete` и **возвращали `{ok:true}`,
игнорируя `error`**. На сбое БД пользователь видит «готово», а записи нет:
- `POST /api/report` — жалоба на нарушителя терялась, не попадая в очередь
  модерации (**safety-critical**: сигнал об абьюзе молча исчезает);
- `POST /api/block` — блокировка (upsert) и разблокировка (delete) — пользователь
  думает, что оградился от нарушителя, а на деле нет (**safety-critical**);
- `POST /api/chats/[id]/messages` — сообщение «отправлено», но не сохранено
  (потеря данных; вдобавок на сбое всё равно слался пуш и обновлялся чат).

Контраст: `onboarding/profile/photo` и `auth/bootstrap` ЭТУ проверку уже имели
(`if (error || !inserted) return 500`) — то есть это локальные пропуски, а не
системное отсутствие паттерна. Инвариант 8 (смена статуса только через
`transition()`) и инвариант 1 (телефон/доки/селфи не в публичном API) — соблюдены
(проверено грепом; `telegram_id` в публичных роутах используется только для
серверного бот-уведомления и в ответ клиенту не утекает).

**Как починили.** В каждый из трёх роутов добавлена проверка результата записи:
при `error` (или отсутствии вставленной строки) — `500 {ok:false}` ДО уведомлений
и до ответа об успехе. Happy-path не меняется.

**Как проверили.** `pnpm typecheck` чисто · `pnpm test:run` 98 зелёных · `eslint`
по изменённым файлам чисто. (Юнит-тестов на роуты в проекте нет по соглашению —
тесты чисто-юнитовые; те же гварды в photo/bootstrap тоже без тестов. Проверка —
типчек + ревью.)

**Бэклог (тот же класс, отложено — медленнее/ниже импакт):** onboarding-апсёрты
(`consent`/`document`/`quiz`/`selfie`/`profile/*`) тоже не проверяют `error` — на
сбое шаг выглядит сохранённым, и пользователь застревает. Импакт ниже (нет потери
UGC/safety-сигнала), вынесено в отдельную итерацию.

## 2026-06-17 · Итерация 3 — онбординг: «сохрани, потом продвигай» (потеря данных в воронке)

**Что нашли (бизнес/воронка-баг).** Все роуты онбординга устроены как
«`upsert/update` данных → `tryTransition()` продвигает шаг». Но **запись данных
игнорировала `error`**, а переход выполнялся всегда. Значит при тихом сбое записи
пользователь **продвигается по воронке с потерянными данными**:
- `profile/basic|family|values|looking-for` — данные анкеты теряются; позже на
  публикации `complete`-чек падает → тупик «profile_incomplete»;
- `document` / `selfie` / `fix` / `retry` — путь к паспорту/селфи не записан, но
  заявка уходит в модерацию → **модератору нечего смотреть** (ложная заявка);
- `quiz/complete` — вектор подбора не сохранён, но пользователь становится
  **active без вектора** → ломается выдача рекомендаций;
- `profile/publish` — `status=published` не записан, но переход на опрос прошёл →
  анкета осталась **неопубликованной** (невидимой), хотя юзеру сказали «ок»;
- `consent` — юридически значимая запись согласия теряется;
- `otp` — `phone_verified_at` не записан (рассинхрон с `phone_verified`).

**Как починили.** Во все 12 роутов: захватываем `error` записи и возвращаем
`500` (`save_failed`/`publish_failed`) **ДО** `tryTransition`. Пользователь
остаётся на текущем шаге и может повторить, данные не теряются. Happy-path не
меняется. `quiz/complete` — проверяются обе вставки (answers + vector).

**Как проверили.** `pnpm typecheck` чисто · `pnpm test:run` 98 зелёных · `eslint`
по 12 изменённым файлам — exit 0.

**Заметка.** Это завершает трилогию одного класса дефектов («тихий сбой БД,
замаскированный под успех»): итер.1 — чтение (тихо-пусто), итер.2 — запись с
ложным «ok» (safety/чат), итер.3 — запись-перед-переходом (воронка). Источник
класса — адаптер `run()`, который мягко возвращает `{data:null,error}`; правильная
дисциплina — всегда проверять `error` (или использовать `unwrap*`).

## 2026-06-17 · Итерация 4 — accept/decline/withdraw интереса: ложный успех + гонка двойного accept

**Аудит (что проверено и ЧИСТО).** Прогнал систематические проверки и зафиксировал
негативные результаты:
- Покрытие auth-гвардами: все 38 API-роутов защищены; без гварда только `health`,
  `admin/login`, `admin/logout` — это и есть публичные/входные точки. ✅
- Админ-логин: троттлинг по IP И по логину; `verifyPassword` использует
  `crypto.timingSafeEqual` (constant-time); `isLoginThrottled` на сбое БД
  **fail-closed** (возвращает «заблокирован»). ✅
- Инвариант 8 (статусы только через `transition()`): прямых UPDATE
  `lifecycle_state`/`verification_status` нет. ✅

**Что нашли (баг).** `POST /api/requests/[id]/decision` (принять/отклонить/отозвать
интерес) имел тот же класс, что итер.2, но в непокрытом роуте — и хуже: на **accept**
`update(status='accepted')` игнорировал ошибку, а код всё равно создавал чат,
слал отправителю «принято» и возвращал ссылку на чат. На тихом сбое: чат есть,
заявка осталась `pending` — рассинхрон. Плюс **гонка двойного accept**: статус
проверялся (select) и менялся (update) неатомарно → два параллельных запроса могли
оба пройти, создав дубль-уведомление/чат.

**Как починили.** Каждый переход — **условный `UPDATE … WHERE status='pending'
RETURNING`**: побеждает только первый (RETURNING вернул строку), остальные получают
`409 not_pending`; чат и уведомление создаются ТОЛЬКО если апдейт реально применился;
ошибка БД → `500`, а не ложный «ok». Атомарно и без ложного успеха одним приёмом.
(`UPDATE … RETURNING` поддержан адаптером — `.update().select()`.)

**Как проверили.** Добавлен юнит-тест в `query-builder.test.ts`: условный апдест с
двумя фильтрами компилируется в `… WHERE "id"=$2 AND "status"=$3 RETURNING *`, и
`data` отражает число затронутых строк (победитель=[row] vs проигравший=[]).
`pnpm test:run` — **99 зелёных** (+1) · `pnpm typecheck` чисто · `eslint` exit 0.

## 2026-06-17 · Итерация 5 — удалённый аккаунт оставался «интерактивным» (privacy + ghost-чаты)

**Что нашли (privacy/бизнес-баг).** `deleted_at` упоминается во ВСЁМ коде лишь
дважды: где ставится при удалении (`account`) и где фильтруется в списке юзеров
админки. Удаление выставляет `lifecycle_state='deleted'` и стирает ПД, **но не
завершает активные связи**:
- висящие интересы удаляемого НЕ отменялись → отправленную заявку получатель мог
  **принять → открывался «призрачный» чат**, а удалившемуся уходил Telegram-пуш
  «ваш интерес принят»;
- в существующих чатах собеседник, отправляя сообщение, **пушил уведомление
  удалившемуся** (строка обезличена, но `telegram_id` сохранён для аудита) — человек
  удалил аккаунт, а уведомления в Telegram продолжают идти.

(Отправить интерес УДАЛЁННОМУ нельзя — `interest` проверяет `lifecycle_state==='active'`.
А вот приём/чаты этой проверки не имели.)

**Как починили (правило: удалённый аккаунт — не интерактивен).**
- `account` (delete): отменяем висящие `match_requests` — отправленные →
  `withdrawn`, полученные → `declined` (только `pending`). Это же закрывает
  ghost-accept: заявка больше не `pending`, итер.4-овский условный апдест вернёт 409.
- `chats/[id]/messages`: перед пушем тянем `lifecycle_state` собеседника и **не
  уведомляем**, если он `deleted`. (Paused — уведомляем: аккаунт жив, может вернуться.)

**Как проверили.** `pnpm typecheck` чисто · `pnpm test:run` 99 зелёных · `eslint`
exit 0. (Роут-тестов в проекте нет по соглашению; логика — последовательность
условных апдейтов, паттерн `.eq("status","pending")` покрыт юнит-тестом адаптера
из итер.4.)

**Бэклог:** существующие чаты с удалённым не «закрываются» (собеседник видит
обезличенный профиль «[удалено]») — отдельная UX-итерация; defense-in-depth в
accept-роуте (проверять, что отправитель ещё active) — опционально, т.к. отмена
заявок при удалении уже закрывает основной путь.

## 2026-06-17 · Итерация 6 — обход анти-контакт фильтра через сообщение интереса (safety/инвариант 1)

**Аудит (что проверено и ЧИСТО).** OTP-сервис (`src/lib/otp/service.ts`): коды
хешируются HMAC-SHA256, генерация `crypto.randomInt` (CSPRNG), TTL 5 мин, ≤5 попыток,
антибомбинг по user_id И по номеру (cooldown 60с + 5/час), старые коды гасятся,
инкремент попыток атомарный (RPC) fail-closed, сбой SMS → не «успех». ✅
`ensureChat` нормализует пару `user_a<user_b` (UNIQUE) + ловит гонку. ✅
`areBlocked` проверяет блок в обе стороны. ✅

**Что нашли (safety-баг).** В чате текст фильтруется `containsContact()` (телефон,
`@username`, ссылки, названия мессенджеров) → `contact_blocked`. Но **сопроводительное
сообщение интереса этой проверки НЕ имело**. То есть анти-контакт политику (инвариант
1: контакты защищены) можно обойти: отправить интерес с текстом «пиши +998901234567 /
@user / telegram», и получатель видит это в «Запросах» — мимо фильтра чата.

**Как починили.** В `POST /api/interest` применил тот же `containsContact()` к
`message` до `process_interest`: при совпадении → `400 contact_blocked` (как в чате).
Единая политика на обоих путях передачи текста между пользователями.

**Как проверили.** `pnpm typecheck` чисто · `pnpm test:run` 99 зелёных · `eslint`
exit 0. Сама `containsContact` уже покрыта юнит-тестами (`schemas.test.ts`: телефон/
username/ссылка/мессенджер + анти-false-positive на годы/диапазоны) — итерация лишь
подключает проверенный фильтр к ещё одному пути.

**Как проверили.** `pnpm lint` exit 0 (было 7 ошибок) · `pnpm typecheck` exit 0 ·
`pnpm test:run` 99 зелёных (конфиг-только изменение, тесты не затронуты).

## 2026-06-17 · Итерация 8 — «фантомные» решения в админ-аудите (целостность журнала, инвариант 7)

**Что нашли (целостность аудита).** Три роута решений модератора. `admin/
verifications` сделан правильно: авторитетный `tryTransition` (атомарно+аудит) с
проверкой `tr.ok` → 409 при сбое. ✅ А вот `admin/photos/[id]/decision` и
`admin/reports/[id]/decision` имели тот же класс «ложного успеха», но с худшим

в админ-аудит** про действие. То есть при тихом сбое БД журнал фиксировал

## 2026-06-17 · Итерация 17 — длинный чат открывался на САМЫХ СТАРЫХ сообщениях (корректность)

**Что нашли (реальный баг чата).** Страница чата `[locale]/chats/[id]` грузила
сообщения `order created_at ASC limit 200` — это **самые СТАРЫЕ 200**. В чате длиннее
200 сообщений пользователь, открыв диалог, видел древнюю историю, а свежие сообщения
**не попадали в окно**. Хуже: `ChatRoom` берёт SSE-курсор из `initial[последний]`
(должен быть НОВЕЙШИМ), а тут это 200-е-с-конца старое → при подключении SSE дампил

по мере роста переписки.

**Как починили.** Грузим **последние** 200 (`order desc limit 200`) и разворачиваем в
ASC для показа. Теперь окно = свежие 200, `initial[последний]` = новейшее сообщение →
SSE-курсор корректен (тянет только реально новое). Совпадает с лимитом 200 в
`getLiveState`.

**Как проверили.** `pnpm typecheck` чисто · `pnpm test:run` 103 зелёных · `eslint`
по странице exit 0. (Логика курсора подтверждена по `chat-room.tsx`:
`cursorRef = initial[initial.length-1].created_at`.)
