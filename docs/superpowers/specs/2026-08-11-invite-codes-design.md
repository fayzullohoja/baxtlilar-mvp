# Коды-приглашения для закрытого запуска

**Дата:** 11.08.2026
**Статус:** согласовано владельцем, готово к плану реализации
**Автор:** проработано в диалоге с владельцем (8 развилок, все решения ниже)

## Зачем

Baxtlilar выходит в закрытый family-запуск. Две цели:

1. **Посторонние не должны заходить.** Войти можно только по коду от человека, который уже внутри.
2. **Должно быть видно, кто кого привёл.** Это и доверие внутри клуба, и рычаг модерации:
   если человек приводит мошенников, это видно.

Шлагбаум **временный**. После запуска выключается тумблером, связи «кто кого привёл»
остаются в истории.

## Принятые решения

| Развилка | Решение | Почему так |
|---|---|---|
| Где шлагбаум | Ссылка подставляет код сама; пришедший сам вводит руками на экране в начале | Удобно тем, кого позвали, и закрыто для случайных |
| Лимит на код | Без лимита, но код можно погасить | Владелец выбрал скорость роста; утечка видна по привязке и гасится кнопкой |
| Кто приглашает | Только с **одобренной верификацией** | Главный тормоз вместо лимита: приглашают лишь подтверждённые люди |
| Что видит пригласивший | **Только число** приглашённых | Имена раскрыли бы третьему лицу факт поиска брака без согласия человека |
| Старт | Разобрать очередь модерации, коды одобренным + мастер-код владельца | Сегодня одобрен только 1 человек, иначе клуб упрётся в него |
| Уже начавшие (15 человек) | Проходят по старым правилам | Телефон и согласия уже отданы; правила не меняют задним числом |
| Бан пригласившего | Код гаснет, вошедших не трогаем | Они не виноваты в поступках пригласившего |
| Горизонт | Временный шлагбаум с рубильником | Меньше кода сейчас, быстрее запуск |

## Поток

Новый шаг стейт-машины `bot_invite_code` между выбором языка и согласием на ПД.

```
bot_language -> bot_invite_code -> bot_consent_pd -> bot_contact -> ...
bot_language -> bot_consent_pd                       (шлагбаум выключен)
```

Обе стрелки из `bot_language` разрешены всегда. Это и есть рубильник: при выключенном
шлагбауме шаг просто пропускается, менять код не нужно.

**Ключевое правило (снимает целый класс ошибок):**

> Шаг показывается, только если код **ещё не зачтён** и человек **не помечен как вошедший
> до запуска**.

Состояние определяется данными, а не последовательностью событий. Поэтому перезапуск
онбординга, повторный вход и любое переключение рубильника ничего не ломают.

### Пришёл по ссылке `t.me/baxtlilar_uz_bot?start=7K2MQX`

1. Telegram присылает `/start 7K2MQX`. **Проверено: аргумент `/start` сейчас ничем не занят**
   (`handleUpdate` разбирает только саму команду), конфликта не будет.
2. Бот проверяет код и запоминает его за пользователем как предъявленный.
3. Человек выбирает язык (этот экран остаётся первым, иначе не на чем говорить).
4. Шаг кода проходится сам: «Приглашение принято» и сразу оферта.

### Пришёл сам

1. Выбирает язык.
2. Экран: «Baxtlilar работает по приглашениям. Введите код».
3. Пишет код текстом. Верный - дальше; неверный - ошибка, остаёмся на шаге.

### Что это даёт

- К моменту проверки известны только Telegram-id и язык. **Ни телефона, ни согласий,
  ни паспорта** - персональные данные непринятых людей у нас не остаются.
- Человек может уйти и вернуться: стейт-машина вернёт его на шаг кода.
- Шаг попадает в воронку Grafana - будет видно, сколько людей упирается в код и уходит.
  Это честная цена закрытого запуска, и её надо измерять.

## Данные

### Таблица `invite_codes`

Коды живут отдельно от людей, чтобы гасить код, не трогая пользователя.

| Поле | Назначение |
|---|---|
| `id` | uuid, первичный ключ |
| `code` | сам код, хранится в верхнем регистре, уникален |
| `owner_id` | чей код; **NULL = мастер-код владельца** (оффлайн-встречи, ручные приглашения) |
| `label` | подпись мастер-кода: «встреча 12.08», «свахи» |
| `disabled_at`, `disabled_reason` | гашение: бан, утечка, вручную |
| `created_at` | когда выдан |

Частичный уникальный индекс: **один активный код на человека** - гарантирует база, а не
аккуратность программиста. Индекс считает только непогашенные коды, поэтому после гашения
(например, код утёк в общий чат) тому же человеку можно выпустить новый - старый навсегда
остаётся погашенным, и по нему видно, кто успел войти до утечки.

### Поля в `users`

| Поле | Назначение |
|---|---|
| `invited_by` | кто привёл; NULL = основатель, мастер-код или вход до запуска |
| `invite_code_id` | какой код предъявлен (нужен для мастер-кодов, где `invited_by` пуст) |
| `invite_redeemed_at` | когда зачтён; пусто + заполненный `invite_code_id` = код из ссылки ждёт шага |
| `invite_exempt` | вошёл до запуска; миграция ставит `true` всем существующим |

Одно поле `invite_code_id` обслуживает оба состояния - разница в том, заполнена ли дата.
Меньше полей, меньше рассинхронов.

**Счётчик приглашённых не денормализуем** - считаем запросом. При наших объёмах это
мгновенно, а дублирование данных рано или поздно разъезжается с правдой.

### Формат кода

6 символов из алфавита без похожих знаков: без нуля и `O`, без единицы, `I` и `L`.
Около 900 миллионов комбинаций - перебрать нельзя, продиктовать по телефону легко.
Регистр и дефисы игнорируются.

### Когда код появляется

В момент одобрения верификации, в той же операции. Подстраховка: если у одобренного кода
нет, он создаётся при первом открытии экрана «Пригласить». Забыть невозможно.

### Рубильник

Через существующий механизм отключения функций (`app_settings` + флаг), тот же, что у чата.
Отдельной сущности не заводим.

## Экраны и тексты

Все тексты нужны на **ru / uz / en**.

**Экран кода в боте:**

> **Baxtlilar сейчас работает по приглашениям**
> Наш клуб пока закрытый: войти можно только по коду от человека, который уже здесь.
> Введите код - или откройте ссылку-приглашение, которую вам прислали.
> `[Нет кода?]`

**По ссылке** экран не показывается, вместо него: «Приглашение принято. Добро пожаловать».

**Ошибки** (формулировки разные, человеку нужно понять, что делать):

| Что случилось | Текст |
|---|---|
| Кода нет | «Такого кода нет. Проверьте раскладку и попробуйте снова» |
| Код погашен | «Этот код больше не действует. Попросите у пригласившего новый» |
| Много попыток | «Слишком много попыток. Попробуйте позже» |

**Не пишем** «код принадлежит заблокированному пользователю» - это раскрыло бы чужой бан
постороннему.

**Кнопка «Нет кода?»**: короткое объяснение («мы растём через личные рекомендации, так
безопаснее для всех») плюс кнопка написать в поддержку. Лазейки нет, но человек не
чувствует себя выброшенным.

**Экран «Пригласить» в мини-аппе** (только при одобренной верификации):

> **Пригласите тех, кому доверяете**
> Ваш код: **`7K2MQX`**
> `[Скопировать ссылку]` `[Поделиться в Telegram]`
> По вашему коду присоединились: **3 человека**

Живёт в настройках профиля; на время закрытого запуска дополнительно плашка на главной.

**Сознательно не делаем:** не показываем имена приглашённых, даты и уведомления
«такой-то зарегистрировался». Только число.

## Краевые случаи

**Кириллица - самая вероятная ошибка нашей аудитории.** В Узбекистане много печатают на
кириллице, и `ВАХТ7К2М` кириллицей выглядит идентично латинскому, но это другие символы.
Человек уверен, что ввёл верно, а бот отвечает «такого кода нет» - самая обидная ошибка.
Перед проверкой приводим похожие кириллические буквы к латинским
(В→B, А→A, Е→E, К→K, М→M, Н→H, О→O, Р→P, С→C, Т→T, У→Y, Х→X), убираем пробелы и дефисы,
поднимаем регистр.

| Случай | Обработка |
|---|---|
| Код погас между переходом по ссылке и шагом | Перепроверяем в момент зачёта, а не только при клике |
| Зарегистрированный жмёт чужую ссылку | Игнорируем. **`invited_by` пишется один раз и навсегда** - иначе историю можно переписать |
| Свой же код | Отдельная проверка, отказ |
| Перезапуск онбординга админом | Invite-поля не трогаем; ключевое правило само пропустит шаг. NB: `admin_restart_onboarding` стирает согласия, паспорт и фото - к invite-полям отношения не имеет |
| Пригласившего разбанили | Код оживает, если гасили именно из-за бана (`disabled_reason='ban'`) |
| Мусор в ссылке (`/start привет`) | Показываем экран ввода |
| Подбор кода | 10 попыток в час на Telegram-аккаунт |

**Известный пробел (осознанный):** код гаснет при бане, но **не при отзыве верификации**.
Человек с отозванным подтверждением сможет приглашать дальше. Закрывается вручную в
админке. Зафиксировано, чтобы не всплыло сюрпризом.

## Админка и аналитика

- **Карточка клиента:** «Пришёл по коду `7K2MQX` от Азиз», «Привёл: 3». Полная картина
  только здесь.
- **Раздел «Приглашения»:** список кодов, владелец, счётчик, кнопка «Погасить»; создание
  мастер-кодов с подписью.
- **Рубильник** - в существующем разделе управления функциями.
- **Grafana:** шаг кода попадает в воронку автоматически (добавляем его в
  `analytics.funnel_steps`), плюс витрина «кто сколько привёл» и доля пришедших по
  мастер-кодам.

## Тесты

- Нормализация: кириллица, пробелы, дефисы, регистр, мусор.
- Валидация: нет кода, погашенный код, свой код, код удалённого пользователя.
- Стейт-машина: переходы при включённом и выключенном шлагбауме.
- Запрет перезаписи `invited_by` у существующего пользователя.
- Гашение кода при бане и оживление при разбане.
- Живой прогон обоих путей: по ссылке и с ручным вводом.

## Порядок выкладки и откат

Порядок обязателен - на этих граблях проект уже стоял (6 миграций не доехали до прода):

1. **Миграция** (значение enum + таблица + поля + пометка существующих) - **до** выкладки кода.
2. **Код** с флагом **выключено по умолчанию**. Для живых людей ничего не меняется.
3. Проверка обоих путей на себе.
4. **Включение флага** осознанно - когда очередь модерации разобрана и у людей есть коды.

**Откат:** выключить флаг. Мгновенно, без деплоя, данные остаются.

## Что НЕ делаем сейчас (YAGNI)

- Награды и бонусы за приглашённых - шлагбаум временный.
- Многоуровневую реферальную программу.
- Очередь ожидания для тех, у кого нет кода (решено: объяснение + поддержка).
- Срок жизни кода.
- Денормализованные счётчики.

## Зависимость вне кода

Перед включением флага нужно **разобрать очередь модерации**: сейчас одобрен 1 человек,
9 дел ждут решения. Иначе приглашать сможет один пользователь. Это работа владельца или
модератора в админке, кодом не решается.
