# Runbook: выкладка

Прод живёт на **своём сервере (VPS, Ташкент)**, домен `https://app.baxtlilar.uz`.
Railway выведен из эксплуатации, см. раздел в конце.

## Стандартный путь

1. Локально:
   ```
   pnpm exec tsc --noEmit && pnpm exec vitest run && pnpm exec next build
   ```
2. `git push origin main` - **сам по себе ничего не выкладывает**. Пуш только
   кладёт код в GitHub.
3. На сервере:
   ```
   sudo baxtlilar-deploy
   ```
   Скрипт делает всё по порядку: бэкап -> `git pull` (`main`) -> зависимости ->
   **миграции** -> сборка -> рестарт -> health.
4. Проверка:
   ```
   curl -sS https://app.baxtlilar.uz/api/health
   ```
   Ожидается `{"ok":true,"db":true,...}`.

Сборка и рестарт занимают около минуты.

## Миграции

Лежат в `supabase/migrations/` (название историческое, это просто SQL).
Применяет `baxtlilar-migrate` - у него свой учёт в таблице `schema_migrations`
со сверкой sha256, поэтому дважды одна миграция не применится, а изменённый
задним числом файл будет замечен.

```
sudo baxtlilar-migrate status   # что применено, что ждёт
sudo baxtlilar-migrate apply    # накатить ожидающие
```

Отдельно руками звать не нужно: `baxtlilar-deploy` вызывает `apply` сам, до
сборки нового кода.

**Права в миграциях не пишем.** Миграции выполняет `postgres`, поэтому новые
таблицы и функции принадлежат ему, а приложение ходит под ролью `baxtlilar` -
`baxtlilar-migrate` пересдаёт права сам после каждого применения (grant роли
приложения, revoke execute у public). Именно поэтому `grant ... to baxtlilar`
нет ни в одной миграции - это не упущение.

⚠️ Разрушающие миграции (DROP, TRUNCATE) - отдельный аудит и снимок БД до.

## Откат

```bash
git revert <hash>
git push origin main
```
затем `sudo baxtlilar-deploy` на сервере. Бэкап перед каждым выкатом делается
автоматически, база - через restic (`/var/backups/baxtlilar/restic`).

## Smoke-чеки после выкладки

```bash
curl -sS -o /dev/null -w "%{http_code}\n" https://app.baxtlilar.uz/api/health
curl -sS -X POST -o /dev/null -w "%{http_code}\n" https://app.baxtlilar.uz/api/telegram/webhook
curl -sS -X POST -o /dev/null -w "%{http_code}\n" -H "Content-Type: application/json" -d '{}' https://app.baxtlilar.uz/api/account
```

Первый должен быть `200`, остальные - `401` и `403`. Non-200 у двух последних =
защита на месте.

Защищённые страницы (`/admin/*`, `/<locale>/v2/*`) незалогиненному отвечают
`200` со страницей входа или «Откройте в Telegram» - это норма, а не дыра.

## Railway: выведен из эксплуатации

Проект `compassionate-serenity`, сервис `baxtlilar-mvp`. Погашен 10.08.2026
после переезда на свой сервер (требование резидентности ПД РУз).

**12.08.2026 отключён автодеплой.** До этого сервис был подписан на пуши в
`main` и вставал сам после каждого пуша - 12.08.2026 он так и воскрес, отдавая
приложение со СТАРОЙ базой. Опасность не в счёте за хостинг, а в расколе: старые
закладки ведут в старую админку, и правки модератора уходят в пустоту.

Что сделано (через публичный API Railway, проектный токен):
- удалён триггер деплоя (`deploymentTriggerDelete`) - объект, который слушал
  пуши в `main`;
- шаблоны отслеживания файлов выставлены в заведомо несовпадающие
  (`serviceInstanceUpdate`, `watchPatterns`) - второй рубеж на случай, если
  триггер кто-то пересоздаст через интерфейс.

Репозиторий формально всё ещё привязан к сервису: `serviceDisconnect` проектному
токену недоступен (`Bad Access`), нужен вход в аккаунт. На автодеплой это уже не
влияет, но если захочется убрать и привязку - только руками в интерфейсе Railway
либо после `railway login`.

База `Postgres-8jAv` намеренно оставлена включённой как страховка отката.
Когда она перестанет быть нужна - проект можно удалить целиком.
