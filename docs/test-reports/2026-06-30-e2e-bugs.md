## Найденные баги

### ✅ Bug #1 — Publish endpoint проверяет dropped V2 поля — FIXED

**File:** `src/app/api/onboarding/profile/publish/route.ts`

**Что не так:** publish endpoint проверял старые V2-поля при валидации полноты профиля:
- `p.city` — в V3 удалено из формы Экрана 1 (basic), осталась только `region`
- `p.values` — колонка ДРОППНУТА в миграции Sprint 3 cleanup (заменена на `top_life_values`)
- `p.looking_for_gender` — V3 transitions skip `profile_looking_for` экран

Результат: при попытке publish юзер получал 400 `profile_incomplete` хотя анкета полностью заполнена.

**Reproduced:** в live-тесте 30.06.2026, юзер на `profile_preview` после прохождения 10 V3 экранов.

**Fix:** заменил select+check на V3 поля. Коммит `97cfb80`.

**Verify:** после deploy → publish вернул `{ok:true, next:"/v2/quiz"}` и state ушёл в `quiz`.

### ⚠️ Bug #2 — verification_case не создаётся при upload селфи — NOT FIXED

**File:** `src/app/api/onboarding/selfie/route.ts` (или должно быть в нём)

**Что не так:** когда юзер загружает селфи и переходит в `verification_status = pending_review`, **никакая строка в `verification_cases`** не создаётся. Single backfill в миграции `20260627100100_verification_cases.sql` сделан только для ПРЕДСУЩЕСТВУЮЩИХ pending_review юзеров на момент миграции — новые юзеры в админ-очередь не попадают.

**Эффект:** модератор не видит в `/admin/queue/*` нового pending юзера. Очередь верификации немая для всех новых регистраций.

**Reproduced:** live test → upload passport → upload selfie → user.verification_status=pending_review → user_documents.status=pending_review → но `select count(*) from verification_cases = 0`.

**Workaround в тесте:** ручной `INSERT INTO verification_cases (user_id, state) VALUES (...)`.

**TODO Fix:** в selfie/route.ts после `verification_status = pending_review` транзакции добавить:
```ts
await supabaseAdmin().from("verification_cases").insert({
  user_id: user.id, state: "new"
});
```
с обработкой случая когда case уже есть (idempotent).

### ✅ Bug #3 — recommend.ts + get_recommendations RPC селектят dropped 'values' — FIXED

**File:** `src/lib/matching/recommend.ts:22` + `supabase/migrations/20260626000000_v2_recommendations_viewer_gate.sql:23,36`

**Severity:** CRITICAL — silent feature failure для ВСЕХ verified юзеров.

**Что не так:** `recommend.ts:22` делает `select("city, values, birth_date")` где колонка `values` ДРОПНУТА в Sprint 3 cleanup (миграция `20260629000000_drop_deprecated_v2_fields.sql`). Supabase-js при ошибке колонки молча возвращает `data=null`, guard на :26 ставит `return []`. RPC `get_recommendations` тоже селектит `vp.values as vals` и `cp.values as vals` — на проде RPC падает. Результат: `main/page.tsx:80` всегда показывает "Алгоритм ищет подходящего человека" — feed не работает ни для кого.

**Reproduced:** теоретически (verifier подтвердил через чтение кода) — у нас сейчас 1 active юзер, но feed empty проверяемо.

**Fix:**
1. Создана миграция `20260630000000_recommendations_v3_top_life_values.sql` — пересоздаёт RPC с `top_life_values` вместо `values`. Применена на проде.
2. `recommend.ts` — select `top_life_values` вместо `values`; правильное приведение в `ScoreInput`.

### ✅ Bug #4 — Ready state dead-end (interrupted tutorial) — FIXED

**File:** `src/app/api/onboarding/welcome/route.ts`

**Severity:** CRITICAL — юзер навсегда застревал.

**Что не так:** tutorial route делает ready→active отдельной второй транзакцией (`tutorial/route.ts:86-96`). Если она падает (DB/network/crash), юзер остаётся `onboarding_step='ready'` и `lifecycle_state='onboarding'`. Router отправит на `/v2/welcome`, но welcome route отвергает `ready` как `wrong_step`. Полный тупик — только ручной DB edit.

**Fix:** welcome route теперь распознаёт `ready` и завершает финальный переход `ready → active + lifecycle_state=active`. ALLOWED_TRANSITIONS.ready=["active"] уже разрешает это.

### ✅ Bug #5 — Non-UZ users заблокированы при публикации — FIXED

**File:** `src/app/api/onboarding/profile/publish/route.ts`

**Severity:** CRITICAL — non-UZ юзеры не могли опубликовать профиль.

**Что не так:** publish endpoint требовал `p.region` truthy безусловно, но `basicSchema` ставит region обязательным **только** для UZ-резидентов (`country_of_residence === "UZ"`). Юзер с country=RU валидно сохраняет profile с region=null, потом publish ловит 400 `profile_incomplete` навсегда.

**Fix:** условная проверка — region обязателен только если country_of_residence === 'UZ'.

---

### ✅ Bug #6 — familyChildrenSchema не enforces conditional fields — FIXED

**File:** `src/lib/profile/schemas.ts:185-192`

**Severity:** MAJOR — приёмка логически неконсистентных данных.

**Что не так:** `children_count` и `youngest_child_age` были `.optional().nullable()` без refine. Кто угодно мог POSTить `{has_children:'yes'}` без count/age и сохранить.

**Fix:** добавлен `.refine()` — если `has_children` не `no`/`na`, то оба поля обязательны.
